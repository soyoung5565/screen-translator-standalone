### 二、修掉的真实 bug

1. **没有全局热键**
   - 原 `keyPressEvent` 只在面板有焦点时生效。打游戏/看视频时面板根本没焦点，
     README 写的 `Ctrl+S` 等于完全失效。
   - 现用 win32 `RegisterHotKey` 注册 `Ctrl+Alt+S/H/Q`（加 Ctrl+Alt 前缀避免和游戏冲突），
     `QAbstractNativeEventFilter` 拦 `WM_HOTKEY` 转 Qt 信号。
   - **坑**：`HotkeyFilter` 必须同时继承 `QAbstractNativeEventFilter`，
     否则 `installNativeEventFilter` 报 `argument 1 has unexpected type`。

2. **覆盖层初始位置错**
   - `overlay.show()` 前没 `setGeometry`，第一帧译文会贴到 (0,0) 附近。
   - 已改为在 `show()` 前同步 `capture_region.geometry()`。

3. **「刷新间隔」滑块是死控件**
   - 滑块只改了标签文字（`3s`→`5s`），worker 里 `time.sleep` 固定，值从未被读取。
   - 现 `configure(..., interval=v)` 真正生效，运行中拖动立即应用。
   - 采样固定 0.35s（保证抓得到变化），API 调用按 interval 节流，
     避免动态画面（视频/游戏）每帧都烧额度。

4. **`.env` 行内注释被当成值**
   - `MINIMAX_CN_BASE_URL=https://api.minimax.cn/anthropic  # 官方中国站...`
     整行被读进 base_url，请求打到 `https://...anthropic  # 官方.../v1/messages` → **HTTP 404**。
   - 现 `_load_dotenv` 去掉「空格 + #」之后的内容，且不误伤 URL 里的 `#`。

### 三、渲染保真度（核心修复）

**问题**：贴上去的中文比原文小一大截，且白底遮罩盖不住英文，变成中英叠字。

**根因（全部实测确认，不靠推理）**：
- 旧 `_fit_font` 把字号 clamp 到 **9pt**。实测：16px 高的原文溢出到 150%，
  56px 高的标题只占 43%，中间尺寸全部失配。
- 遮罩 alpha 只有 160，原文英文会透出来。

**修复**：
1. 放弃 `pointSize`，改用 `setPixelSize`（不受 DPI 影响）。
2. 用 `calibrate_font.py` 实测标定 YaHei 的字形比例：
   ```
   墨高 ≈ 0.99 × 像素字号      →  像素字号 ≈ 1.01 × 目标高度
   墨高 ≈ 0.76 × fm.height()
   ```
   **不要**拿 `fm.height()` 当字号依据 —— 它含行距，比真实墨高大 ~1.3 倍。
   （中间版本就是被这个系数带偏，中文墨高只剩原文 54%。）
3. 遮罩 alpha 提到 230（≈90% 遮盖）。
4. **配色自适应**：`TextBlock` 带上 `bg_lum`（worker 从截图采样，取中位数 ——
   平均会被文字墨迹拉偏，最亮在深底白字时取到的是字本身）。
   - 浅底 → 白罩 + 深红字
   - 深底 → 深罩 `#121418` + 浅绿字 `#8cf0aa`
   （否则深色标题栏上会出现一块刺眼的白斑。）
5. **模型框兜底**：模型给的 `h` 偶尔严重偏小（实测出现过 3px、7px，原文实际 17~22px），
   `w` 也常偏窄。现在：
   - `h < 11px` 或 `h < 中位数×0.65` → 用中位数并按中心对齐
   - `w < max(h×3, 60px)` → 加宽（遮罩必须盖住整句原文）
6. **空结果重试**：模型偶尔返回 `[]`，且空数组会被缓存住。
   重试前清掉该 cache key，最多 3 次，取块数最多的结果。

### 五、测量脚本踩过的坑（都是自己挖的）

写量化测试时，判定函数连续错 5 次，每次都让指标看起来"有 bug"：

1. 把红色描边算进译文墨迹 → 高度永远"超标"。
2. 把"接近纯白"算成英文墨迹 → 白色遮罩被统计成未遮盖的英文。
3. 只判亮度不判色相 → 深红中文（lum≈45）被当成英文墨迹，遮盖率永远 25~45%。
4. 用 90 分位估背景亮度 → 取到白字本身，深色标题栏被误判成浅底，遮盖率算出 **-584%**。
5. 统计窗口把框宽 +60px → 把相邻行的英文算进来，遮盖率虚低到 9~28%。

**结论：先打印原始像素值确认，再写判定函数。** 视觉模型对这类图的描述也不可靠
（它报告"中文系统性偏上 15~20px"和"英文后半截残留"，像素实测分别是 +0.5px 和残留 0）。

### 六、已知限制

- **模型 JSON 偶发语法损坏**：实测抓到 `"x":39","y":52`（数字后多一个引号）。
  已在 `_repair_json` 里修补，`parse_json_boxes` 四级降级解析。回归用例
  `test_parse_repair.py` 用的就是这段真实坏输出，不是构造样例。
- **长译文向右溢出**：有意为之 —— 宁可向右多出一截，也不缩字到看不清。
- **深色底配色**按背景亮度分档（阈值 110），交界处（如半透明面板）可能选错。
- **动态内容**（视频/游戏）靠 interval 节流，间隔设太小会持续烧额度。

## 2026-10-28 · 根治「漏行」：三个真 bug（都不是模型能力问题）

上一轮把「同一张图每次返回 0~5 块」记为「模型能力上限」。这一轮抓原始响应
才发现它由三个确定性缺陷叠加造成，**全部修掉后同一张图 6/6 次采样稳定返回 5/5 行**。

### 一、提示词参数错位（漏行主因）

`build_boxes_prompt` 的规则 4 是「只识别 %s 原文」，那个 `%s` 本应是**源语言**，
实际传的却是 `tname`（目标语言）。默认 `target=zh` 时提示词变成：

> 4. **只识别中文原文**。如果图里已经出现中文文字…

英文界面里当然没有"中文原文"，模型于是"正确地"忽略它 —— 返回 `[]`
或零星几块。这个错位一直在，之前所有"模型漏行"的诊断都建立在这条错误提示词上。

修法：`source="auto"` 时改写为「识别图中所有**可翻译的原语言**文字」，
显式指定源语言时写「只需识别 X 原文」。

### 二、JSON 修补（漏行另一半）

抓到的原始响应（`stop_reason: end_turn`，5 行齐全）：

```json
[{"t":"Control Panel","x":39","y":52,"w":198,"h":34,"zh":"控制面板"}, ...]
```

注意 `"x":39","y"` —— **数字后面多了一个引号**。整段不是合法 JSON：

- `json.loads` 直接抛异常；
- 退回的 `\{[^{}]*\}` 逐对象兜底很脆，救回 0~3 个对象；
- 最终表现就是"漏行"。

新增 `_repair_json()` 处理实测见过的三种破坏，`parse_json_boxes` 改为四级降级
（原样 → 修补 → 逐对象 → 逐对象+修补），每级取条数最多的结果。
回归用真实样本，见 `test_parse_repair.py`。

### 三、重试条件写错

`translate_image_boxes` 原逻辑是 `if best: break` —— 拿到**任意**块就停。
返回 1 块时根本不重试，等于「块数越少越不重试」。改为按块数判断
（`< MIN_BOXES(3)` 继续重试），取块数最多的结果。

## 墨迹校正：用像素反推真实文字框

模型给的 `w/h/x/y` 系统性不准，且这是**渲染优化治不了**的：

| 实测偏差 | 后果 |
|---|---|
| `h` 只有真实的 40~60%（出现过 3px / 7px，真值 17~22px） | 译文字号缩到看不清 |
| `w` 偏窄 | 遮罩盖不住整句英文，后半截露出来 |
| `y` 偏移几像素 | 译文与原文错位，读起来像叠字 |

`refine_blocks_with_ink()` 拿截图**实测的墨迹包围盒**反推真实框：
按行统计墨迹 → 找连续行带 → 取带内左右极值。

**关键实现约束（踩过两次）**：
- 搜索窗尺度**绝不能用当前块的 h 推** —— h 就是最大误差源。
  `±0.35×h` 时 h=8 的窗口只有 11px 高，22px 的真行只扫到顶部 6px，
  校正后 IoU 反而从 0.09 掉到…（实测 0.20，比不改更差）。
  改用带 12px 下限的 `unit` 做尺度基准。
- 兜底上限也不能用中位数 h 推 —— 那批 h 本身偏小，真行会被判"离谱"而放弃校正。
- 背景亮度改从框**外侧一圈**采。框内中位数会被粗体白字带偏：
  26px 白字标题实测框内算出 lum=88（真背景 42），离阈值 110 太近会翻车。

**确定性回归证据**（`test_render_fidelity.py`，故意把真值坐标劣化
h×0.4 / w×0.55 / y-2px，模拟模型典型噪声）：

```
                          遮盖率        垂直Δ      字高比
坏坐标（未校正）     75.0 ~ 84.8%    -2.0px    0.71 ~ 1.08   ✗ 5/5 不达标
坏坐标 + 墨迹校正   100.0% (全部)    ≤1.5px    0.94 ~ 1.05   ✓ 5/5 达标
```

**对抗场景**（`test_ink_refine.py`，全部 IoU = 1.000）：

| 场景 | 结果 |
|---|---|
| 4 行独立校正（h 压到 40%、w 砍到 55%、x+3、y-4） | 4/4 IoU 1.000（校正前 0.06~0.09） |
| 密集行距（行距 26px ≈ 1.2×字高） | 4/4 落在自己那一行，无串行 |
| 同行双块（左标签 + 右数值） | 2/2 IoU 1.000，**无越界**吃进邻居 |
| 纯色图 / `img=None` | 原样返回，不崩 |

性能：1920×1080 下 20 个块耗时 **69ms**（纯 Python 逐像素），
相对一次视觉 API 调用（数百 ms~数秒）可忽略。

**测试真值本身也会踩坑**（两次）：
- 扫描窗贴着色块边界 → 深浅交界被算成墨迹，真值框膨胀到 410×50。
- 密集行距用固定 ±12px 窗扫 → 吃进上一行下伸部，真值 45..68（实际 51..68），
  "标准答案"本身是错的，会误判校正为串行。
  改法：真值用**逐行单独渲染**再量墨迹。

## 其他修复

| 项 | 问题 | 修法 |
